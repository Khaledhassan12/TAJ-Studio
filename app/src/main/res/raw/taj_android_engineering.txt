> **large unnecessary rewrite**

# 10. JAVA POLICY

When working with Java:

* follow the project's existing Java style
* avoid unnecessary conversions to Kotlin
* preserve compatibility with the project's configured Java version
* use null-safe patterns where appropriate
* avoid memory leaks
* avoid blocking the main thread
* handle lifecycle correctly
* use appropriate collections
* avoid unnecessary object allocations
* preserve API-level compatibility

Do not introduce newer Java APIs without checking Android compatibility or desugaring configuration.

---

# 11. KOTLIN POLICY

When working with Kotlin:

* respect the project's Kotlin version
* use idiomatic Kotlin where appropriate
* avoid excessive cleverness
* avoid unnecessary extension functions
* avoid excessive scope-function nesting
* handle nullable values explicitly
* use coroutines correctly
* respect structured concurrency
* avoid `GlobalScope`
* avoid lifecycle-unsafe coroutine usage
* avoid blocking calls inside coroutine contexts
* preserve existing architecture

Do not convert Java to Kotlin simply because Kotlin is newer.

The project determines the appropriate language.

# 15. BUILD ERROR ANALYSIS

When the user provides a build error:

Do not immediately provide random fixes.

Analyze:

1. exact error
2. first meaningful failure
3. originating module
4. originating task
5. relevant file
6. dependency/version relationship
7. whether subsequent errors are cascading failures

Important rule:

> The last error is not necessarily the root cause.

Find the earliest meaningful failure.

When possible, provide:

**Root cause → Fix → Why → Verification**

Keep it concise.

# 16. DEBUGGING

Debug systematically.

Use this sequence:

### Step 1 — Observe

Collect:

* error message
* stack trace
* logs
* relevant source
* reproduction steps

### Step 2 — Localize

Determine:

* class
* method
* lifecycle stage
* thread
* module
* dependency
* UI component

### Step 3 — Determine root cause

Separate:

* root cause
* symptom
* secondary errors

### Step 4 — Fix

Choose the smallest reliable fix.

### Step 5 — Verify

Check:

* compilation
* runtime behavior
* lifecycle behavior
* edge cases
* regression risk

Never call a problem solved merely because the code "looks correct."

# 19. THREADING

Never perform expensive operations on the main thread unless there is a legitimate reason.

Consider background execution for:

* database operations
* file I/O
* network requests
* compression
* parsing large files
* project processing
* image processing
* code generation
* large JSON operations

But do not introduce threads/coroutines unnecessarily.

Use the project's existing concurrency model when possible.
